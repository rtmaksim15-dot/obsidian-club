## АРХИТЕКТУРА ПРОДУКТА

### Ecosystem Rule
> Каждая фича должна усиливать минимум 3 существующих системы. Если не усиливает — не строим.

### Houses System
Тематические дома внутри клуба. Каждый дом = своя культура, контент, продукты.

**Phase 1 (текущий приоритет):**
- **House of Rope** — шибари/кинбаку вертикаль

**Следующие фазы:** ещё 9 домов (leather, protocol, impact и др.)

### The Vault
Заменяет концепцию "магазина". Доступ к эксклюзивному контенту и продуктам открывается через репутацию — не через деньги напрямую.

### Signature Rope Collection
- Ежегодные лимитированные коллекции: 250 единиц
- Пронумерованные, с сертификатом, с системой передачи (transfer registry)
- Верёвка как коллекционный артефакт — этого нет ни у одного конкурента

Полный аудит "что ещё видно вне v1-скоупа" — см. TECH_DEBT.md
- **v1 — компрессия фото + редирект Community** — реальные фото с iPhone всё ещё падали с "Image must be 8MB or smaller" даже после фикса signed URL. Добавлена клиентская компрессия (`lib/utils/compressImage.ts`: canvas, максимум 2048px по длинной стороне, JPEG ~0.85) перед загрузкой — применена и к фото постов, и к аватару; HEIC идёт через тот же общий пайплайн без отдельной обработки. `/rooms` теперь редиректит сразу в единственную активную комнату (Newcomers), минуя список из одного пункта и ссылку Events — чисто по данным (`rooms.length === 1`), без флага; когда активируется вторая комната, индекс вернётся сам
- **v1 — Members & Follows** (`OBSIDIAN_ROADMAP_v3.1`): `/members` — простой список активных участников (аватар, имя, строка bio), сортировка по дате вступления; фильтр/поиск — только когда участников станет больше ~30. Вход — ссылка "Members →" в шапке комнаты Newcomers. Модель `Follow` + `POST /api/users/:id/follow` (тот же toggle-паттерн, что у лайков); кнопка Follow/Following и строка "N followers · N following" на каждом публичном профиле. Лента остаётся общей хронологией — подписки её пока не фильтруют. Отзывы (список + форма) на `/profile/[username]` теперь тоже за `REP_UI_ENABLED`. `PostCard`/`PostList` получили режим `compact` (без повтора аватара/имени) — используется в "Your Posts" на `/hall`. Устаревшее уведомление "Your access has been granted" теперь пропадает автоматически после завершения ритуала
- **v1 — Invitation & Partner system** (`OBSIDIAN_ROADMAP_v3.1`): три способа создать аккаунт, помимо старой Waitlist-заявки. **Purchase cards** — `/admin/invite-batches` генерирует пачку из N токенов со сквозной нумерацией (не сбрасывается между пачками), без заявки и привязки к email; CSV-экспорт для печати. **Member invites** — `inviteAllowance` (по умолчанию 1, меняется вручную через БД), блок "My Invitation" на `/hall` — кнопка "Create invitation" делает персональную одноразовую ссылку; при регистрации — `invitedById` на новом участнике + тихая строка "Invited by [имя]" на публичном профиле. Старый `/?ref=` — насовсем выключен. **Partner** — отдельно от инвайтов, не тратит allowance; "Add partner" делает одноразовую ссылку, после регистрации — "Partner of [имя]" на профилях обеих сторон (по одному партнёру на участника). Все три источника гасятся через один `POST /api/join/:token`, токен становится недействителен сразу после использования — без исключений по источнику. REP/Referral/Trust Score сознательно не подключены ни к одному из трёх новых путей — см. TECH_DEBT.md
- **Batch generator v2** (reconciliation addendum, 2026-08-14): `InviteToken` получил жизненный цикл — `shortCode` (`OBS-XXXX-XXXX`, ручной ввод без сканирования), `status` (`unused|opened|activated|expired|revoked`), `validUntil` (жёсткий потолок 90 дней от генерации), `firstScannedAt`/`clientExpiresAt` (окно 7 дней от первого скана `/join/[token]`), `revokedAt`. Оба новых срока — nullable, чтобы не трогать 2 реальных уже выданных токена от 08.08 (см. TECH_DEBT.md, DECISIONS.md). По пути закрыта настоящая гонка: два одновременных `POST` на один токен больше не могут создать два аккаунта. Генератор теперь кладёт в пачку QR-PNG на каждый токен (`GET .../qr-zip`) и расширенный CSV (short code + ссылка на реальном домене вместо `NEXT_PUBLIC_APP_URL`); админ-борд (`/admin/invite-batches`) показывает счётчики по статусам и умеет Revoke/Arm/смену source по токену. `/join` — ручной ввод короткого кода как альтернатива QR. Полный прогон сценариев (арминг, оба терминальных состояния, one-time burn, гонка redemption, rate limit, RLS, consent+ritual) — на тестовой QA-TEST пачке, удалённой после; реальная Batch 01 (500 purchase_card, № 1-500) сгенерирована и экспортирована

6. **Обновляй этот файл** когда статус задачи меняется
7. **Никогда не удаляй контент, который ты не создавал в текущей сессии
   с явным тестовым маркером** (2026-08-01, после реального инцидента:

   сообщения, файлы) должны создаваться с префиксом `test-` в
   имени/username, либо явно логироваться в момент создания в рамках
   той же сессии — это единственный источник истины о том, что
   безопасно удалять. Всё остальное — реальные данные участников,
   трогать нельзя. **Если есть малейшее сомнение — спросить в чате, не
   удалять.** Это касается и Prisma-строк, и файлов в Supabase Storage:
   оба вида удаления необратимы (нет soft-delete/корзины), в отличие от
   обратимых действий вроде переключения фичи-флага.
8. **После любого `prisma db push` / миграции — проверяй RLS**
   (`npm run check:rls`). RLS был выключен на 22 из 24 таблиц с
   16.07.2026 до 04.08.2026 незамеченным — никто не проверял, потому что
   не было автоматической проверки. Когда её наконец написали
   (06.08.2026), она с первого запуска поймала повторение той же самой
   проблемы: `rate_limit_hits`, добавленная той же сессией парой дней
   раньше, осталась без RLS, потому что попала в схему уже после
   основной миграции-зачистки. Новая таблица без RLS — это не
   гипотетический риск, он уже реализовывался дважды подряд. Скрипт
   (`scripts/check-rls.ts`) — это не рекомендация, а обязательный шаг
   сразу после любого изменения `prisma/schema.prisma`, которое трогает
   БД.
9. **Любая запись в JSON-поле (`ritualProgress` и любое другое) —
   read-merge-write, никогда plain overwrite.** Инцидент 07.08.2026:
   одноразовый бэкфилл-скрипт (Task 1, username-in-the-ritual) записал
   `ritualProgress: { usernameChosen: true }` без предварительного

   Obsidian, хотя там оказалось нечего терять), из-за чего ритуал
   откатился на "TO DO" для уже прошедшего его живого пользователя.
   Оба постоянных API-роута (`app/api/profile/route.ts`,
   `app/api/ritual/progress/route.ts`) всегда мержили правильно
   (`{ ...progress, key: true }`) — баг был именно в одноразовом
   скрипте вне репозитория. Любой будущий одноразовый скрипт,
   трогающий JSON-поле на реальном аккаунте, обязан сначала прочитать
   текущее значение и замёржить в него изменение, а не просто
   присвоить новый объект.
